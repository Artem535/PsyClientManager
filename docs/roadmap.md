# PsyClientManager — технический ROADMAP развития продукта

**Статус:** Draft  
**Горизонт:** текущая версия → 1.0  
**Тип документа:** технический roadmap с описанием продуктовых функций  
**Проект:** PsyClientManager

---

# 1. Назначение документа

Документ определяет развитие PsyClientManager как локального приложения для
управления частной психологической практикой.

Roadmap описывает:

- какие функции уже входят в продукт;
- каких пользовательских сценариев не хватает;
- в каком порядке добавлять новые возможности;
- какие изменения потребуются в архитектуре, модели данных и интерфейсе;
- какие функции требуют внешних сервисов;
- какие функции могут работать полностью локально;
- какие критерии определяют готовность каждого этапа.

Основной приоритет — улучшение текущего desktop-приложения. Облачные функции,
мобильный клиент и AI рассматриваются как последующие расширения, а не как
обязательная основа продукта.

# 2. Назначение PsyClientManager

PsyClientManager — local-first desktop-приложение для психологов,
психотерапевтов и других специалистов, ведущих индивидуальную практику.

Приложение должно объединять:

- расписание;
- клиентскую базу;
- историю консультаций;
- заметки и вложения;
- учёт оплаты;
- напоминания;
- аналитику практики;
- резервное копирование;
- защиту чувствительных данных.

Основная копия данных хранится локально. Базовые функции не должны зависеть от
интернета, собственного backend или обязательной регистрации.

# 5. Направление A — улучшение текущего рабочего процесса

## 5.1. Цель

Устранить недостатки уже существующих функций и сократить количество ручных
действий при ежедневной работе.

## 5.2. Новые функции

### Расширенные статусы встречи

Добавить статусы:

- запланирована;
- подтверждена;
- проведена;
- перенесена;
- отменена клиентом;
- отменена специалистом;
- клиент не пришёл.

Статус оплаты должен храниться отдельно от статуса встречи.

### Причина отмены

Для отменённых встреч добавить предустановленные причины, пользовательский
комментарий и возможность учитывать или не учитывать отмену в аналитике.

### Подтверждение встречи

Добавить отметку подтверждения клиентом, фильтр неподтверждённых встреч,
визуальный индикатор в Timeline и быстрое копирование сообщения с просьбой
подтвердить встречу.

### Буфер между встречами

Пользователь должен иметь возможность задать минимальный перерыв между
консультациями, отдельный буфер до и после встречи и исключения для конкретных
событий.

### Разные типы консультаций

Добавить справочник типов: индивидуальная, парная, первичная, повторная,
онлайн, очная и пользовательские типы.

Для типа консультации можно задать стандартную длительность, стоимость, цвет,
шаблон приглашения и способ проведения.

### Улучшение Quick Slots

Добавить выбор продолжительности слота, создание нескольких слотов, копирование
списка свободного времени, фильтрацию по рабочим дням, учёт буферов, исключение
личных событий и шаблон сообщения со свободными интервалами.

### Список задач на день

На главном экране показывать встречи на сегодня, неподтверждённые встречи,
неоплаченные консультации, встречи без заметки, просроченные действия, ошибки
backup и ошибки синхронизации.

# 7. Направление C — резервное копирование и восстановление

## 7.1. Цель

Исключить потерю клиентской базы из-за повреждения файла, ошибки обновления или
удаления каталога.

## 7.2. Функции

### Ручной и автоматический backup

В настройках добавить кнопку создания backup, выбор каталога, описание
содержимого и дату последней успешной копии. Автоматический backup должен
поддерживать закрытие приложения, ежедневный и еженедельный режимы, запуск перед
обновлением схемы, импортом, восстановлением и массовым удалением.

### Политика хранения

Пользователь задаёт максимальное количество копий, срок хранения, сохранение
недельных и месячных копий и исключение отдельных копий из удаления.

### Restore Wizard

Пользователь выбирает файл, видит дату и версию приложения, проверяет целостность,
восстанавливает данные, отменяет операцию и может вернуть состояние до
восстановления.

### Проверка backup

Нужны отдельные проверки архива, базы, вложений и отсутствующих или повреждённых
файлов.

## 7.3. Формат backup

Предлагаемый формат: `*.psybackup`.

```text
manifest.json
database.duckdb
attachments/
checksums.json
```

```json
{
  "backup_format_version": 1,
  "schema_version": 5,
  "application_version": "0.2.0",
  "backup_uuid": "...",
  "workspace_uuid": "...",
  "device_uuid": "...",
  "created_at": "...",
  "attachments_count": 42
}
```

## 7.4. Технические изменения

Добавить `BackupService`, `RestoreService`, `BackupValidator` и
`BackupRotationService`.

Порядок создания backup:

1. Заблокировать новые операции записи.
2. Завершить текущие транзакции.
3. Создать согласованный snapshot DuckDB.
4. Скопировать вложения.
5. Рассчитать checksum.
6. Проверить созданный snapshot.
7. Записать временный архив.
8. Атомарно переименовать архив.
9. Снять блокировку записи.

Простое копирование открытого файла DuckDB не считается корректной реализацией.

## 7.5. Критерии готовности

- backup включает базу и вложения;
- повреждённый backup обнаруживается;
- восстановление проходит во временный каталог;
- текущая база не удаляется до успешной проверки;
- существует автоматический тест полного восстановления;
- ротация не удаляет последнюю рабочую копию.

# 8. Направление D — приватность и защита данных

## 8.1. Цель

Защитить информацию от случайного просмотра, копирования backup и чтения файлов
приложения.

Нужно добавить приватные уведомления в трёх режимах: полный текст с именем,
скрытый текст «запланирована консультация» и минимальный текст без деталей.
Скрытый режим используется по умолчанию.

Также нужны PIN или пароль, ручная и автоматическая блокировка после бездействия,
блокировка после sleep и опционально при сворачивании. Блокировка интерфейса не
заменяет шифрование файлов.

В production-логи нельзя записывать имена, телефоны, email, тексты заметок,
диагнозы, полные ссылки встреч, OAuth-токены и ключи шифрования.

Для чувствительных данных добавить автоматическую очистку clipboard с
настраиваемой задержкой.

## 8.2. Критерии готовности

- персональные данные не показываются в уведомлениях по умолчанию;
- приложение блокируется после заданного интервала;
- production-логи не содержат PII;
- PIN не хранится в открытом виде;
- после разблокировки пользователь возвращается на прежний экран.

# 9. Направление E — шифрование

Шифрование внедряется поэтапно: сначала backup, затем системное хранилище ключа,
рабочая база и вложения.

## 9.1. Шифрование backup

Нужны зашифрованный `.psybackup`, пароль восстановления, проверка и смена
пароля, восстановление на другом компьютере и понятное сообщение о невозможности
восстановить забытый пароль.

```text
Recovery password
        ↓
Argon2id
        ↓
Key encryption key
        ↓
Encrypted random master key
        ↓
Authenticated encrypted backup
```

Рекомендуется libsodium. Самостоятельная реализация криптографических алгоритмов
не допускается.

## 9.2. Хранение ключа

Для автоматических операций ключ хранится в системном secret storage через
QtKeychain: Windows Credential Manager, macOS Keychain, Secret Service или KWallet.
В конфигурации хранится только идентификатор ключа.

## 9.3. Рабочая база и вложения

Нужно исследовать поддерживаемое DuckDB-шифрование и зафиксировать совместимую
версию библиотеки. Вложения хранятся как `attachments/<uuid>.enc`, расшифровываются
во временный каталог только на время открытия и затем удаляются.

## 9.4. Критерии готовности

- изменение ciphertext обнаруживается;
- неправильный пароль не повреждает данные;
- ключи не записываются в логи;
- backup восстанавливается на другом устройстве;
- миграция начинается только после проверенного backup;
- незашифрованная старая база удаляется не сразу.

# 10. Направление F — экспорт и переносимость

## 10.1. Пользовательские функции

Экспорт клиента включает карточку, встречи, заметки, статусы, оплаты и список

## 10.2. Технические изменения

Добавить `ClientExportService`, `CalendarExportService`,
`AnalyticsExportService` и `ImportService`. JSON должен иметь собственную версию

## 10.3. Критерии готовности

- экспорт не требует интернета;
- ICS корректно работает с повторяющимися событиями;
- CSV импортируется с предварительным просмотром;
- ошибка одной записи не отменяет весь импорт без отчёта.

# 11. Направление G — облачное резервное копирование

## 11.1. Папка пользователя

Первый этап работает через каталог на внешнем диске, Syncthing, Nextcloud,
Yandex Disk, OneDrive, Dropbox или другом синхронизируемом хранилище.

PsyClientManager отвечает только за создание зашифрованного backup, а внешний
клиент — за доставку файла в облако.

Нужны выбор каталога, проверка доступности, отображение свободного места,
автоматическое копирование, повтор после ошибки и уведомление о неуспешной
выгрузке.

## 11.2. Storage Provider API

После стабилизации файлового режима можно добавить адаптеры:

```cpp
class StorageProvider {
 public:
  virtual AuthResult connect() = 0;
  virtual UploadResult upload(...) = 0;
  virtual DownloadResult download(...) = 0;
  virtual std::vector<RemoteBackup> list() = 0;
  virtual DeleteResult remove(...) = 0;
};
```

Возможные реализации: WebDAV, Yandex Disk, Nextcloud и S3-compatible storage.
OAuth-токены хранятся в системном keychain.

## 11.3. Ограничение

Облачный backup не является полноценной синхронизацией. Первая версия позволяет
сохранить, перенести и восстановить данные, но не редактировать одну базу на
нескольких устройствах одновременно.

## 11.4. Критерии готовности

- в облако отправляется только encrypted backup;
- незавершённая загрузка не заменяет предыдущую копию;
- ошибка облака не блокирует приложение;
- отключение аккаунта не удаляет локальные данные;
- удалённый backup можно скачать и проверить.

# 12. Направление H — синхронизация устройств

## 12.1. Первая версия — snapshot sync

```text
Локальная база
      ↓
Encrypted snapshot
      ↓
Удалённое хранилище
      ↓
Другой компьютер
```

Нужны определение более новой версии, загрузка и отправка snapshot, UUID
устройства, история поколений, обнаружение конфликта и сохранение обеих версий.

```json
{
  "workspace_uuid": "...",
  "generation": 24,
  "backup_uuid": "...",
  "device_uuid": "...",
  "created_at": "...",
  "content_hash": "..."
}
```

При конфликте пользователь выбирает локальную версию, удалённую версию,
сохранение обеих версий или откладывает решение. Автоматический merge базы не
входит в первую версию.

## 12.2. Будущее operation-based sync

```text
ChangeLog
- operation_uuid
- entity_uuid
- entity_type
- operation_type
- revision
- device_uuid
- created_at
- encrypted_payload
```

Такой механизм значительно сложнее и не должен блокировать выпуск `1.0`.

# 13. Направление I — уведомления и интеграции

## 13.1. Локальные уведомления

Добавить приватный режим, отдельные настройки рабочих и личных событий,
уведомления повторяющихся событий, несколько напоминаний, уведомления о
неоплаченной встрече, напоминание заполнить заметку, ошибках backup и конфликтах
синхронизации.

## 13.2. Подготовленные сообщения

Добавить действия копирования приглашения, открытия Telegram с подготовленным
текстом, открытия email-клиента, копирования свободных интервалов и сообщений о
переносе или отмене. Отправка остаётся под контролем пользователя.

## 13.3. Календарь и Telegram

Первая версия интеграции с календарём — ICS с приватным названием, alarm и
повторениями. Следующая версия может добавить CalDAV, Google Calendar и Outlook
Calendar с сопоставлением внешнего и локального события.

Telegram-бот — отдельный поздний этап. Он может напоминать специалисту,
подтверждать встречу, отправлять ссылку и уведомлять о переносе, но не входит в
обязательный roadmap до `1.0`.

# 14. Направление J — PsyNote companion

## 14.1. Цель

Создать мобильное приложение для расписания и локальных уведомлений без переноса
всей клиентской базы.

## 14.2. MVP

Расписание на сегодня и неделю, локальные уведомления, открытие ссылки на
видеовстречу, просмотр типа консультации, приватный режим и отображение времени
последнего обновления.

Минимальный schedule snapshot:

```text
event_uuid
start_at
end_at
private_title
meeting_url
reminder_offsets
status
```

Не передаются диагнозы, полные заметки, вложения, финансовая аналитика и
дополнительная информация клиента.

# 15. Направление K — OCR, поиск и AI

## 15.1. OCR и полнотекстовый поиск

OCR должен поддерживать импорт изображения, распознавание, предпросмотр,
коррекцию, сохранение оригинала, привязку к клиенту и поиск по тексту. Первая
версия работает локально либо явно предупреждает об отправке изображения во
внешний сервис.

Поиск должен охватывать клиентов, заметки, события, теги, вложения и OCR-текст.

## 15.2. AI-ассистент

Возможные функции: резюме истории клиента, структурирование черновика заметки,
поиск связанных записей, подготовка вопросов к следующей встрече и поиск по
пользовательской базе знаний.

Обязательно явное включение, выбор локальной или облачной модели, показ
отправляемых данных, возможность удалить персональные поля, отсутствие скрытого
обучения и журнал операций без сохранения полного чувствительного текста.

AI не входит в обязательный состав `1.0`.

# 16. Подготовка модели данных

Для будущих backup, export и sync необходимо заранее добавить стабильные UUID
для workspace, device, client, event, event series, note, attachment, client
task, consultation type и backup. Числовые ID могут остаться внутренними ключами.

Для основных сущностей нужны:

```text
created_at
updated_at
deleted_at
revision
origin_device_uuid
```

Добавить системную таблицу:

```text
ApplicationMetadata
- schema_version
- backup_format_version
- workspace_uuid
- created_at
- last_migration_at
```

Каждая миграция должна иметь уникальный номер, запускаться после backup,
проверять исходную версию, логировать результат, иметь автоматический тест и
корректно завершаться после перезапуска.

# 20. Функции, которые пока не следует реализовывать

До завершения основной desktop-версии не рекомендуется начинать realtime sync,
центральную базу пользователей, командные пространства, управление клиникой,
собственную видеосвязь, автоматическую отправку SMS, сложного Telegram-бота,
web-версию, server-side AI и совместное редактирование.

Эти функции увеличивают инфраструктурную и продуктовую сложность, но не
устраняют основные недостатки текущего приложения.
